# Data Model: Add Project Members

**Feature**: `008-add-project-members` | **Phase**: 1 | **Date**: 2026-08-18

## Entity Overview

| Entity | Ownership | Purpose |
|--------|-----------|---------|
| User | Feature 001 prerequisite | Current account role/status and membership subject/actor identity |
| Project | Features 002/007 prerequisite | Private work container, key, and active/archived status |
| Project Membership | Feature 008 extension | One historical period in which a user is assigned to a Project |
| Notification | Shared with features 004/006 | Unread in-app alert for one membership-add event |
| Project Activity Entry | Shared with feature 004 | Durable Project history item for one membership-add event |

Feature 008 MUST extend the shared Notification and Project activity schemas if they already exist. It MUST NOT create parallel feature-specific tables that duplicate those shared concepts.

## Prerequisite Entities

### `users`

Required fields from feature 001:

| Field | Required semantics |
|-------|--------------------|
| `id` | UUID primary key |
| `role` | `admin` or `member` |
| `status` | `active` or `suspended` |
| `first_name`, `last_name` | Display identity for membership controls and messages |
| `email` | Stable account identity; not emitted into activity payloads |

An actor is eligible to add a user only when the current database row is `role = admin` and `status = active`. A selected user is eligible for Project Membership only when the current database row is `status = active`; both Admin and Member accounts may be assigned, including the acting Admin's own account. Active and suspended are the complete account-status set for this feature.

### `projects`

Required fields from features 002/007:

| Field | Required semantics |
|-------|--------------------|
| `id` | UUID primary key |
| `key` | Unique 2–6 character external Project identifier |
| `name` | Notification and membership-page label |
| `status` | `active` or `archived` |

Project status is read dynamically at authorization time. A Project Membership does not copy or freeze status-based permissions.

## `project_memberships`

Each row represents one uninterrupted assignment period. Removal is modeled for compatibility with feature 002, although removal behavior is outside feature 008.

| Field | Type / constraint | Meaning |
|-------|-------------------|---------|
| `id` | UUID primary key, generated by database | Stable identity for this assignment period and its side effects |
| `project_id` | UUID, not null, foreign key to `projects.id` | Assigned Project |
| `user_id` | UUID, not null, foreign key to `users.id` | Assigned user |
| `added_by_user_id` | UUID, not null, foreign key to `users.id` | Admin who performed the add |
| `added_at` | timestamptz, not null, database time | Commit-time membership start |
| `removed_by_user_id` | UUID, nullable, foreign key to `users.id` | Admin who later removed the membership |
| `removed_at` | timestamptz, nullable | End of this membership period |

### Constraints and indexes

- Primary key: `id`.
- Partial unique index `project_memberships_one_active_per_user` on `(project_id, user_id)` where `removed_at IS NULL`.
- Check constraint: `removed_at` and `removed_by_user_id` are either both null or both non-null.
- Index `(user_id, removed_at)` for current Project lists.
- Index `(project_id, removed_at, added_at)` for Project membership display.
- Foreign-key deletion behavior is restrictive; account and Project deletion are not part of this feature.

### Derived state

| State | Predicate | Access consequence |
|-------|-----------|--------------------|
| Active membership | `removed_at IS NULL` | User may discover and access the Project according to current Project status |
| Historical membership | `removed_at IS NOT NULL` | No current Project access; row remains for history and side-effect references |

## `notifications`

This is the shared in-app Notification entity. Feature 008 adds or uses the following shape for `project_member_added`.

| Field | Type / constraint | Meaning |
|-------|-------------------|---------|
| `id` | UUID primary key | Notification identity |
| `recipient_user_id` | UUID, not null, foreign key to `users.id` | Added user |
| `actor_user_id` | UUID, not null, foreign key to `users.id` | Admin who added the user |
| `kind` | constrained value, not null | `project_member_added` |
| `project_id` | UUID, not null, foreign key to `projects.id` | Destination Project |
| `project_membership_id` | UUID, not null, foreign key to `project_memberships.id` | Deduplication/source identity |
| `read_at` | timestamptz, nullable | Null means unread; later behavior is owned by shared Notification features |
| `created_at` | timestamptz, not null, database time | Notification creation time |

### Constraints and indexes

- Unique `(kind, project_membership_id)` prevents duplicate membership-add Notifications.
- Index `(recipient_user_id, read_at, created_at DESC)` supports unread/recent recipient reads.
- The destination is derived from the referenced Project key; no client-supplied URL is stored.
- Display names are resolved from current User and Project rows; no uncontrolled text payload is required.

## `project_activity_entries`

This is the shared Project history entity. Feature 008 adds or uses the following shape for a membership-add event.

| Field | Type / constraint | Meaning |
|-------|-------------------|---------|
| `id` | UUID primary key | Activity identity |
| `project_id` | UUID, not null, foreign key to `projects.id` | Feed owner |
| `actor_user_id` | UUID, not null, foreign key to `users.id` | Admin who performed the add |
| `event_type` | constrained value, not null | `member_added` |
| `subject_user_id` | UUID, not null, foreign key to `users.id` | Added user |
| `project_membership_id` | UUID, not null, foreign key to `project_memberships.id` | Deduplication/source identity |
| `created_at` | timestamptz, not null, database time | Event time |

### Constraints and indexes

- Unique `(event_type, project_membership_id)` prevents duplicate add activity.
- Index `(project_id, created_at DESC, id DESC)` supports stable reverse-chronological feed reads.
- The activity renderer resolves actor and subject names from User references; it does not accept free-form event text from the action.

## Relationships

```text
users (actor) 1 ──< project_memberships >── 1 projects
users (member) 1 ──< project_memberships
project_memberships 1 ── 1 notifications(kind=project_member_added)
project_memberships 1 ── 1 project_activity_entries(event_type=member_added)
users (recipient) 1 ──< notifications
projects 1 ──< notifications
projects 1 ──< project_activity_entries
```

## Add-Member Transaction

The domain transaction receives validated `projectId`, `selectedUserId`, and the authenticated session identity.

1. Read the actor from the database and require active Admin state.
2. Read the selected user under the account-mutation lock discipline established by feature 001 and require active state.
3. Read the Project and require it to exist; active or archived status is allowed and does not change membership-creation eligibility.
4. Insert one active `project_memberships` row.
5. If the partial unique index reports an active duplicate, map it to `already_member` and roll back.
6. Insert the `project_member_added` Notification using the returned membership ID.
7. Insert the `member_added` Project activity entry using the same membership ID.
8. Commit, then return success and revalidate mutation-relevant paths.

Any failure before commit rolls back all three inserts. Unexpected failures never return membership success. Because Notification persistence is part of the transaction, temporary UI staleness does not create a missing Notification and never weakens the committed membership.

## State Transitions

```text
Eligible active user + no active membership
  └── Admin add commits ──> Active Project Membership
                              ├── unread project_member_added Notification
                              └── member_added Project activity entry

Active Project Membership
  ├── duplicate add ──> unchanged + already_member result
  └── future remove (feature 002) ──> Historical Project Membership

Historical Project Membership
  └── later re-add ──> new Active Project Membership period
                       + new Notification + new activity entry
```

Project `active ↔ archived` transitions do not modify or reject Project Membership rows, including when status changes during an add. Access is calculated from active membership plus current Project status whenever access is evaluated.

## Read Models

### Membership management page

- Current members: active membership joined to minimal User display fields, ordered by normalized name then stable user ID.
- Candidate options: all current users with derived state `eligible`, `already_member`, or `suspended`; the acting Admin is treated like any other active candidate.
- Empty state: when no `eligible` candidate remains, explain that all active accounts are already assigned while keeping unavailable reasons distinguishable.
- Only an active Admin may receive this combined read model.

### Recipient Project list

- Include Projects joined through `project_memberships.removed_at IS NULL`.
- Archived Projects remain included but carry read-only status.
- Never expose private Projects through a historical or absent membership.

### Recipient Notification list

- Filter by `recipient_user_id` from the current session.
- Order unread first according to shared Notification behavior, then `created_at DESC` with `id DESC` as a stable tie-breaker.
- Resolve the destination as `/projects/{project.key}`.

## Retention and Privacy

- Membership history retention follows feature 002; Notification retention and read state follow feature 006; Project activity retention follows feature 004. Feature 008 introduces no deletion controls.
- Candidate queries expose account status only to Admins on the Project membership page.
- Notifications expose only the recipient's own records.
- No raw email, session token, free-form client event text, or external destination URL is copied into membership side effects.
