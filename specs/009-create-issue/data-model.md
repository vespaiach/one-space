# Data Model: Create Issue

**Feature**: `009-create-issue` | **Phase**: 1 | **Date**: 2026-08-20

## Entity Overview

| Entity | Ownership | Purpose |
|--------|-----------|---------|
| User | Feature 001 prerequisite | Creator, assignee, and project-member identity |
| Project | Features 002/007 prerequisite | The container an issue belongs to; supplies name/key/color for the composer breadcrumb |
| Project Membership | Feature 008 prerequisite | Determines who may create issues in a project and who may be assigned |
| Issue | Feature 009 | The work item being created |
| Label | Feature 009 | A project-scoped, reusable tag; created ahead of time or inline |
| Issue Label | Feature 009 | Many-to-many association between Issue and Label |

Feature 009 extends the shared `projects`, `project_memberships`, and `users` tables read-only; it does not modify their schemas.

## Prerequisite Entities

### `users` (feature 001)

| Field | Required semantics |
|-------|--------------------|
| `id` | UUID primary key |
| `role` | `admin` or `member` |
| `status` | `active` or `suspended` |
| `first_name`, `last_name` | Display identity for the assignee picker |

### `projects` (features 002/007)

| Field | Required semantics |
|-------|--------------------|
| `id` | UUID primary key |
| `key` | Unique 2–6 character external identifier, used only for breadcrumb display in this feature |
| `name`, `color` | Composer breadcrumb label and dot |
| `status` | `active` or `archived` |

### `project_memberships` (feature 008)

| Field | Required semantics |
|-------|--------------------|
| `project_id`, `user_id` | Identify one membership period |
| `removed_at` | Null means the membership is currently active |

A user may create an issue for a project, and may be selected as its assignee, only while an active (`removed_at IS NULL`) `project_memberships` row exists for that user and project. This is the same predicate `getProjectAccessByKey` already uses for the project page.

## `issue_status` (enum)

Fixed values, in board order: `backlog`, `todo`, `in_progress`, `done`, `canceled`. Display labels: "Backlog", "Todo", "In Progress", "Done", "Canceled". Default: `backlog`.

## `issue_priority` (enum)

Fixed values: `none`, `low`, `medium`, `high`, `urgent`. Display labels: "No Priority", "Low", "Medium", "High", "Urgent". Default: `none`.

## `issues`

| Field | Type / constraint | Meaning |
|-------|-------------------|---------|
| `id` | UUID primary key, generated by database | Issue identity |
| `project_id` | UUID, not null, FK → `projects.id`, `onDelete: restrict` | Owning project |
| `title` | `varchar(255)`, not null | Required; rejected if blank after trimming |
| `description` | `text`, nullable | Raw markdown source; rendered by `lib/markdown/render.ts` on read |
| `status` | `issue_status`, not null, default `backlog` | Current column |
| `priority` | `issue_priority`, not null, default `none` | Priority level |
| `assignee_id` | UUID, nullable, FK → `users.id`, `onDelete: restrict` | At most one assignee |
| `created_by` | UUID, not null, FK → `users.id`, `onDelete: restrict` | Creator |
| `created_at` | `timestamptz`, not null, database time | Creation timestamp |
| `updated_at` | `timestamptz`, not null, database time | Reserved for future edit features; set equal to `created_at` on insert |

### Constraints and indexes

- Primary key: `id`.
- Index `(project_id, status)` for future per-column reads.
- Index `(assignee_id)` for future "assigned to me" reads.
- Title is validated in application code (non-empty after trim, ≤255 chars) rather than a check constraint, consistent with how `projects.name` is validated in `lib/projects/validation.ts`.
- Description, when present, is validated in application code (≤10,000 chars), matching `projects.description`'s existing limit.

## `labels`

| Field | Type / constraint | Meaning |
|-------|-------------------|---------|
| `id` | UUID primary key, generated by database | Label identity |
| `project_id` | UUID, not null, FK → `projects.id`, `onDelete: restrict` | Scope |
| `name` | `varchar(50)`, not null | Display name; case-preserved as typed |
| `color` | `varchar(20)`, not null | One of the six `label` StyleX token keys (`design`, `bug`, `content`, `research`, `infra`, `a11y`), assigned by cycling on the project's current label count |
| `created_by` | UUID, not null, FK → `users.id`, `onDelete: restrict` | Who created the label (inline or otherwise) |
| `created_at` | `timestamptz`, not null, database time | Creation timestamp |

### Constraints and indexes

- Primary key: `id`.
- Unique index `labels_project_name_unique` on `(project_id, lower(name))` — enforces case-insensitive uniqueness per project and is the concurrency guard for Edge Case "two users simultaneously type the same new label name."
- Index `(project_id)` for the label-picker read.

## `issue_labels`

| Field | Type / constraint | Meaning |
|-------|-------------------|---------|
| `issue_id` | UUID, not null, FK → `issues.id`, `onDelete: cascade` | Owning issue |
| `label_id` | UUID, not null, FK → `labels.id`, `onDelete: restrict` | Applied label |

### Constraints and indexes

- Composite primary key `(issue_id, label_id)` — an issue cannot carry the same label twice.
- Index `(label_id)` for future "filter by label" reads.

## Relationships

```text
users (creator)   1 ──< issues
users (assignee)  1 ──< issues                (0 or 1 per issue)
projects          1 ──< issues
projects          1 ──< labels
issues            1 ──< issue_labels >── 1 labels
project_memberships ── gates who may create an issue for / be assigned within a project
```

## Create-Issue Transaction

The domain transaction (`lib/issues/create-issue.ts`) receives the validated `projectId`, `title`, `description`, `status`, `priority`, `labelSelections` (existing label IDs plus zero or more new label names), `assigneeId | null`, and the authenticated session identity.

1. Re-read the current session and require an active account; re-read project membership for `(projectId, session.userId)` and require an active row — otherwise reject as `forbidden` (FR-001, FR-002).
2. Validate `title` (non-empty, ≤255 chars), `description` (≤10,000 chars if present), `status`, and `priority` against their enums — otherwise return field errors (FR-003, FR-006, FR-009).
3. For each new label name requested: `INSERT ... ON CONFLICT (project_id, lower(name)) DO NOTHING RETURNING id`; if no row returns, `SELECT id FROM labels WHERE project_id = $1 AND lower(name) = lower($2)` to get the existing (or concurrently-inserted) label's ID instead (FR-012, FR-013, concurrency edge case).
4. If `assigneeId` is present, re-check active project membership for `(projectId, assigneeId)`; if it is no longer active, proceed with `assignee_id = null` and flag `assigneeCleared: true` in the result rather than failing (FR-016).
5. Insert one `issues` row with the resolved `status` (default `backlog` if omitted), `priority` (default `none` if omitted), `assignee_id`, and `created_by = session.userId`.
6. Insert one `issue_labels` row per resolved label ID (existing, reused, or newly created) referencing the new issue's ID.
7. Commit. Any failure before commit rolls back all inserts, including any label rows created in step 3 for labels that end up unused by this issue (label creation and issue creation are one atomic unit, so a failed issue insert does not leave an orphaned label).
8. Return success (with `assigneeCleared` if applicable) and revalidate the project's issue-related paths.

## Validation Rules Summary

| Field | Rule | Source |
|-------|------|--------|
| Title | Required; trimmed; 1–255 chars | FR-003 |
| Description | Optional; ≤10,000 chars; markdown escaped before rendering | FR-004, FR-005 |
| Status | Must be one of the five `issue_status` values | FR-006, FR-008 |
| Priority | Must be one of the five `issue_priority` values | FR-009 |
| Label name (inline create) | Trimmed; 1–50 chars; case-insensitively unique per project | FR-012, FR-013 |
| Assignee | Must be an active project member at submission time, or is cleared | FR-014, FR-016 |

## Read Models

### New Issue page composer

- Project header: `name`, `color`, `key` from `projects`, read via the same `getProjectAccessByKey`-style query the project page already uses (also enforces FR-002 for the page itself).
- Assignee options: active project members, `project_memberships` joined to `users` where `removed_at IS NULL`, ordered by name — reuses the existing `lib/db/queries/project-members.ts` read.
- Label options: `labels` where `project_id = $1`, ordered by `name` — new `lib/db/queries/labels.ts` read.

## Out of Scope for This Feature

- Editing, deleting, commenting on, or viewing a full detail page for an issue.
- Renaming, deleting, or reordering statuses/columns (fixed enum; no customization).
- A human-readable Issue Key/number.
- Notifications or activity-feed entries for issue creation.
- Any live/push propagation mechanism beyond synchronous commit-then-read.
